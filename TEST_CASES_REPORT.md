## 4. Common procedures

### Core UI precondition

1. Boot and unlock the selected emulator; install or upgrade the intended APK without clearing Wallet data.
2. Start Appium and launch Wallet with its existing authenticated session.
3. Confirm the dashboard is visible before starting a case; capture the case ID, build, device, and initial UI state.

### Controlled SMS precondition

1. Use a disposable QA identity with known test-owned accounts and starting balances; verify SMS reception permission and supported account suffix.
2. Record the exact starting account values and counts. Construct a single synthetic SMS with unique run marker and a known expected outcome.
3. Inject through the emulator only. Wait for processing, inspect the real app UI, then verify values after navigation and process restart.
4. Delete only the uniquely tagged record and confirm balances return to their pre-test values. Remove the exact injected SMS from the emulator inbox and verify it is absent.

### Result labels

- **Passed:** the assertion succeeded on the real app and evidence exists.
- **Failed:** a reproducible product assertion failed, with test setup and expected behavior confirmed.
- **Inconclusive:** test harness, product requirement, or oracle was insufficient to judge app behavior.
- **Not run / gated:** steps are defined but need isolated data, product decision, or physical device before execution.
